# Практическая работа: Перегрузка операторов в C++

## 1. Что такое перегрузка операторов и зачем она нужна

**Перегрузка операторов** — возможность определить собственное поведение
стандартных операторов языка (`+`, `-`, `==`, `<<`, `[]`, `++` и т.д.) для
пользовательских типов. Формально это разновидность **специального
синтаксиса вызова функции**: запись `c1 + c2` для объектов класса `Complex`
компилятор превращает в вызов `c1.operator+(c2)` (или
`operator+(c1, c2)` для дружественной функции) — то есть перегрузка
оператора — это просто функция с необычным именем и особым синтаксисом
вызова. Отсюда происходит термин **"синтаксический сахар"** (syntactic
sugar): за красивой записью `c1 + c2` скрывается обычный вызов метода,
который можно было бы записать явно как `c1.add(c2)`, но запись через
оператор ближе к математической нотации и делает код интуитивно понятным.

Главная цель перегрузки — дать пользовательским типам (`Complex`,
`Fraction`, `Matrix`, `Polynomial`) такой же естественный, "встроенный"
синтаксис использования, как у примитивных типов языка (`int`, `double`).

## 2. Функция-член vs дружественная функция: почему выбор не случаен

При перегрузке оператора приходится выбирать между двумя формами
реализации, и этот выбор диктуется не вкусом, а **синтаксическими
ограничениями языка**:

### Почему `operator+` — функция-член, а `operator/` — дружественная

Когда оператор реализован как функция-член, **левый операнд всегда
подразумевается как `*this`** — то есть выражение `c1 + c2` буквально
означает `c1.operator+(c2)`, и первый (левый) операнд обязан быть объектом
именно этого класса. Для `+`, `-`, `*` в задании это не создаёт проблем,
потому что оба операнда — объекты `Complex`.

Однако **операторы ввода/вывода `<<` и `>>` обязаны быть дружественными
функциями (или свободными функциями), а не функциями-членами**, потому что
их **левый операнд — это `ostream`/`istream`** (`cout`, `cin`), а не
объект пользовательского класса. Если бы `operator<<` был методом
`Complex`, пришлось бы писать `c << cout`, что противоречит естественному
чтению `cout << c`. Стандартная библиотека C++ не позволяет добавлять
методы в `std::ostream` для каждого нового пользовательского типа, поэтому
единственный способ — свободная (обычно дружественная, чтобы иметь доступ к
приватным полям) функция вида `ostream& operator<<(ostream& os, const
Complex& c)`.

`operator/` в задании реализован как дружественная функция скорее по
стилистическим соображениям (симметрия операндов), хотя технически мог бы
быть и функцией-членом, как `+`. Общее правило: если оба операнда должны
быть **равноправно** приводимы (например, чтобы `5 + c` работало наравне с
`c + 5` за счёт неявного преобразования числа в `Complex` через
одноаргументный конструктор), оператор делают свободной/дружественной
функцией — тогда компилятор может применить неявное преобразование к
**обоим** аргументам, а не только к правому.

### Правила языка (что нельзя делать при перегрузке)

1. **Нельзя создавать новые операторы** — можно перегрузить только те
   символы, что уже существуют в языке (`+`, `%`, `<<=` и т.д.), но нельзя
   изобрести, например, оператор `**` для возведения в степень.
2. **Нельзя менять арность** — унарный оператор (`!a`) остаётся унарным,
   бинарный (`a + b`) — бинарным.
3. **Нельзя менять приоритет и ассоциативность** — `a + b * c` всегда
   вычислит `b * c` первым, независимо от того, как реализованы `+` и `*`
   для пользовательского типа.
4. **Хотя бы один операнд должен быть пользовательским типом** — нельзя
   переопределить `operator+` для двух `int`, потому что это изменило бы
   поведение встроенного языка.

## 3. Разбор ключевых решений в заданиях

### Задание 1 — Complex: зачем результат — новый объект, а не изменение `this`

`operator+`, `operator-`, `operator*` **не изменяют** `real`/`imag`
исходных объектов, а создают и возвращают **новый** объект `Complex`. Это
соответствует поведению встроенных арифметических операторов: выражение
`a + b` для `int` тоже не меняет `a` и `b`, а порождает новое значение. Если
бы `operator+` менял `this`, то `c1 + c2` работало бы как `c1 += c2`, что
удивило бы любого, кто пишет `Complex sum = c1 + c2;`, ожидая, что `c1`
останется неизменным.

### Задание 2 — Fraction: почему только `<` реализуется "по-настоящему"

В классе `Fraction` только `operator==` и `operator<` содержат
самостоятельную логику сравнения (через перекрёстное умножение
`numerator * other.denominator` вместо приведения к `double`, чтобы
избежать погрешностей округления чисел с плавающей точкой). Все остальные
операторы сравнения **выражены через них**:

```cpp
bool operator!=(...) const { return !(*this == other); }
bool operator>(...)  const { return other < *this; }
bool operator<=(...) const { return (*this < other) || (*this == other); }
bool operator>=(...) const { return (*this > other) || (*this == other); }
```

Это классический приём **уменьшения дублирования и минимизации риска
ошибок**: если логику сравнения нужно будет изменить или исправить в ней
баг, достаточно поправить `==` и `<` в одном месте — остальные четыре
оператора автоматически останутся согласованными. (Начиная с C++20 эту
идею формализовали в язык напрямую: оператор `<=>` — "оператор
трёхстороннего сравнения" (spaceship operator) — автоматически генерирует
все шесть операторов сравнения из одной реализации.)

### Задание 3 — Counter: почему у инкремента две формы с разными сигнатурами

C++ различает префиксный (`++c`) и постфиксный (`c++`) инкремент чисто
синтаксически — оба имеют одинаковое имя `operator++`, а различаются
**фиктивным параметром `int`**, который у постфиксной формы ничего не
означает семантически, а служит исключительно меткой для компилятора,
чтобы отличить одну перегрузку от другой:

```cpp
Counter& operator++();      // префиксный:  ++c
Counter  operator++(int);   // постфиксный: c++  (int здесь — просто метка)
```

Разные типы возврата — не случайность, а прямое следствие семантики
операций:
- **Префиксный** инкремент сначала изменяет объект, а *затем* возвращает
  **уже изменённое** состояние — поэтому он возвращает **ссылку на *this**
  (`Counter&`): дополнительное копирование не нужно, ведь мы возвращаем тот
  же самый, уже обновлённый объект.
- **Постфиксный** инкремент обязан вернуть значение объекта **до**
  изменения (`c++` в выражении — это старое значение `c`) — поэтому
  реализация сначала сохраняет копию (`Counter temp = *this;`), изменяет
  оригинал, а возвращает именно сохранённую копию **по значению**
  (`Counter`, без `&`) — ссылку вернуть было бы нельзя, так как `temp` —
  локальная переменная, которая перестанет существовать после выхода из
  функции.

Именно поэтому по умолчанию в цикле предпочтительнее `++i`, а не `i++` —
префиксная форма не создаёт лишней копии.

### Задание 4 — DynamicArray: разбор канонической реализации `operator=`

Правильная реализация оператора присваивания всегда следует одному и тому
же шаблону, продемонстрированному в `zadanie4_dynamicarray.cpp`:

```cpp
DynamicArray& operator=(const DynamicArray& other) {
    if (this != &other) {            // 1. защита от самоприсваивания
        delete[] data;                // 2. освободить старый ресурс
        size = other.size;
        data = new int[size];         // 3. выделить новый ресурс
        for (...) data[i] = other.data[i]; // 4. скопировать данные
    }
    return *this;                     // 5. вернуть ссылку на себя
}
```

**Зачем нужна проверка `this != &other`?** Если пропустить эту проверку и
выполнить `arr1 = arr1;` (самоприсваивание), строка `delete[] data;`
освободила бы память, а следующая строка `other.data[i]` попыталась бы
прочитать уже освобождённую (и потенциально перезаписанную) память — это
классическая ошибка **use-after-free**. Проверка на самоприсваивание —
обязательный элемент любого корректного `operator=`, управляющего
ресурсами.

**Зачем возвращать `DynamicArray&`, а не `void`?** Чтобы поддержать
**цепочечное присваивание** — `a = b = c;` компилируется в
`a.operator=(b.operator=(c))`, что требует, чтобы `b.operator=(c)`
возвращало объект, пригодный для дальнейшего присваивания в `a`.

### Задание 5 — Matrix: почему `operator[][]` нельзя перегрузить напрямую

В C++ оператор индексации `operator[]` принимает **ровно один** аргумент —
язык не предусматривает синтаксиса "оператора с двумя парами скобок".
Поэтому `matrix[i][j]` реализуется через **два последовательных вызова**
`operator[]`: `matrix[i]` вызывает `Matrix::operator[](int)`, который
возвращает не число, а **вспомогательный объект `MatrixRow`**, хранящий
указатель на нужную строку. Затем `[j]` — это уже вызов
`MatrixRow::operator[](int)`, который и возвращает ссылку на конкретный
элемент. Такая "цепочка операторов" — стандартный приём эмуляции
многомерной индексации в C++ (начиная с C++23 появился `operator[]` с
несколькими параметрами, но до этого стандарта — только через вложенные
прокси-объекты, как здесь).

Наличие **двух версий** `operator[]` (обычной и `const`) нужно, чтобы
индексация корректно работала как для изменяемых, так и для константных
объектов `Matrix`: `const`-версия возвращает `const double&`, не позволяя
изменить содержимое через константный объект, что сохраняет
константность-корректность (const-correctness) во всей программе.

### Задание 6 — Polynomial: оператор `()` — функторы (function objects)

`operator()` позволяет **вызывать объект как функцию**: `p1(2)` вызывает
`Polynomial::operator()(double x)`, вычисляющий значение многочлена в точке
`x`. Классы, перегружающие `operator()`, называются **функторами**
(function objects) — они широко используются в стандартной библиотеке
(например, компараторы для `sort`, `priority_queue`, о которых пойдёт речь
в практических работах про STL, папки 10–11), потому что, в отличие от
обычных функций и указателей на функции, функтор может **хранить
состояние** (в данном случае — коэффициенты многочлена) между вызовами.

## 4. Реальные области применения

- **Математические и физические библиотеки** (Eigen, GLM для 3D-графики):
  перегруженные `+`, `*`, `[]` позволяют писать `matrixA * matrixB + vecC`
  так же естественно, как арифметику над числами.
- **Умные указатели стандартной библиотеки** (`unique_ptr`, `shared_ptr`)
  перегружают `operator*`, `operator->`, `operator bool`, чтобы вести себя
  синтаксически как обычные указатели, скрывая внутреннюю логику управления
  памятью (см. практическую работу про динамическую память, папка 2).
- **Итераторы контейнеров STL** — это, по сути, объекты, перегружающие
  `operator++`, `operator*`, `operator!=`, что позволяет унифицированно
  обходить `vector`, `list`, `map` в цикле `for` одинаковым синтаксисом
  (подробнее — практическая работа про STL-контейнеры, папка 10).
- **Компараторы для сортировки и очередей с приоритетом** — функторы с
  перегруженным `operator()` задают произвольный порядок сравнения объектов
  (см. практическую работу про STL-алгоритмы, папка 11, где используется
  `greater<int>()` — стандартный функтор).

## 5. Ответы на вопросы для защиты практической работы

**Что такое перегрузка операторов и для чего она нужна?**
Это возможность определить собственную реализацию стандартного оператора
языка для пользовательского типа, чтобы объекты этого типа можно было
использовать так же естественно, как встроенные типы (числа), с помощью
привычной операторной нотации вместо явного вызова именованных методов.

**В чём разница между перегрузкой оператора как функции-члена и как
дружественной функции?**
У функции-члена левый операнд неявно является объектом `*this`, поэтому
такой оператор обязательно требует, чтобы левый операнд был объектом
данного класса. Дружественная (или обычная свободная) функция не привязана
к конкретному операнду и позволяет реализовать операторы, у которых левый
операнд — не объект класса (например, `ostream <<`), либо когда нужна
симметрия неявных преобразований для обоих операндов.

**Какие операторы нельзя перегружать?**
В C++ нельзя перегружать: `::` (доступ к области видимости), `.`
(доступ к члену объекта), `.*` (доступ к члену через указатель на член),
`?:` (тернарный оператор), а также нельзя создавать новые операторы,
отсутствующие в языке.

**В чём отличие префиксного и постфиксного инкремента?**
Префиксный сначала изменяет объект, затем возвращает ссылку на уже
изменённый объект. Постфиксный сохраняет копию текущего состояния,
изменяет оригинал, но возвращает сохранённую копию (старое значение) по
значению. Постфиксная форма отличается от префиксной наличием фиктивного
параметра `int` в сигнатуре.

**Почему оператор присваивания должен возвращать ссылку на *this?**
Чтобы поддерживать цепочечные присваивания вида `a = b = c;`, где результат
одного присваивания сразу становится операндом следующего, и чтобы
избежать ненужного копирования объекта при возврате.

**Зачем нужна проверка if (this != &other) в операторе присваивания?**
Чтобы корректно обработать самоприсваивание (`a = a;`). Без этой проверки
освобождение старого ресурса (`delete[] data;`) уничтожило бы данные до
того, как они были бы скопированы из "источника", который на самом деле —
тот же самый объект.

**Почему операторы << и >> перегружаются как дружественные функции?**
Потому что их левый операнд — это объект потока (`std::ostream`/
`std::istream`), а не объект пользовательского класса, поэтому оператор не
может быть методом пользовательского класса; он реализуется как свободная
функция, а дружественность даёт ей доступ к приватным полям класса.

**Как перегрузить оператор [] для поддержки многомерных индексов?**
В C++ до стандарта C++23 `operator[]` принимает только один параметр,
поэтому многомерная индексация (`m[i][j]`) реализуется через
последовательные вызовы: первый `operator[]` возвращает
вспомогательный (proxy) объект, представляющий "строку", а второй
`operator[]`, определённый уже в этом вспомогательном классе, обращается к
конкретному элементу.

**Что такое синтаксический сахар в контексте перегрузки операторов?**
Термин означает, что операторный синтаксис (`a + b`) — это лишь удобная,
более читаемая запись, которая компилятором превращается в обычный вызов
функции/метода (`a.operator+(b)`). Никакой новой возможности языка при этом
не добавляется — только более естественная запись существующей операции.

**Какие правила нужно соблюдать при перегрузке операторов?**
Нельзя изобретать новые операторы, менять арность, приоритет и
ассоциативность существующих операторов; хотя бы один операнд должен быть
пользовательского типа; поведение оператора должно интуитивно соответствовать
его смыслу для встроенных типов (принцип наименьшего удивления) — например,
`operator+` не должен неожиданно менять состояние операндов.
