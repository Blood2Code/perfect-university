# Практическая работа №4: Наследование и полиморфизм

## 1. Наследование: моделирование отношения "является"

**Наследование** — механизм, позволяющий создать новый класс (производный,
derived class) на основе уже существующего (базового, base class), унаследовав
его поля и методы и добавив или переопределив часть из них. Основная цель —
не просто "не писать код дважды", а **смоделировать реальное отношение
"является"** (is-a relationship): `Rectangle` **является** `Shape`, `Dog`
**является** `Animal`, `Manager` **является** `Employee`. Если такого
смыслового отношения нет, наследование — неверный инструмент (в этом случае
лучше подходит композиция — отношение "содержит", has-a).

`public`-наследование (`class Rectangle : public Shape`) сохраняет
уровни доступа базового класса: то, что было `public` в `Shape`, остаётся
`public` в `Rectangle`. Именно `public`-наследование корректно моделирует
"является" и позволяет использовать объект производного класса всюду, где
ожидается объект базового (принцип подстановки Барбары Лисков, о котором
ниже).

### Порядок вызова конструкторов и деструкторов

При создании объекта производного класса сначала строится **база**, потом
**производный класс** (в `zadanie1_shape.cpp` при создании `Rectangle`
сначала выводится "Конструктор Shape", затем "Конструктор Rectangle").
Логика проста: прежде чем инициализировать специфичные для `Rectangle`
поля (`width`, `height`), должна существовать полностью готовая база,
частью которой является `Rectangle`. При уничтожении объекта порядок
**обратный**: сначала уничтожается производная часть, затем базовая — это
гарантирует, что пока выполняется деструктор `Rectangle`, унаследованные от
`Shape` поля (`color`) ещё существуют и валидны для использования.

## 2. Полиморфизм и виртуальные функции

**Полиморфизм** — способность объектов разных (но родственных по
наследованию) типов реагировать по-разному на один и тот же вызов метода. В
C++ полиморфизм реализуется через **виртуальные функции**.

### Как это работает на уровне реализации: vtable

Когда класс объявляет хотя бы одну `virtual`-функцию, компилятор добавляет к
каждому объекту этого класса скрытый указатель (`vptr`) на **таблицу
виртуальных функций** (vtable) — массив указателей на реальные реализации
методов для конкретного динамического типа объекта. Вызов виртуальной
функции через указатель/ссылку на базовый класс (`animals[i]->speak();` в
`zadanie2_animal.cpp`) на этапе выполнения:

1. Читает `vptr` из объекта (он указывает на vtable конкретного класса —
   `Dog`, `Cat` или `Cow`, в зависимости от того, что реально было создано
   через `new`);
2. По этой vtable находит адрес переопределённой версии метода;
3. Вызывает найденную функцию.

Это называется **динамической диспетчеризацией** (dynamic dispatch) — в
отличие от обычных (невиртуальных) функций, которые разрешаются на этапе
компиляции по статическому типу указателя (**статический полиморфизм**
отсутствует в этом случае — вызывается ровно та функция, тип которой
записан в объявлении переменной).

Именно поэтому в `main()` цикл `for (Animal* a : animals) a->speak();`
выводит разные фразы для `Dog`, `Cat`, `Cow`, хотя тип переменной массива —
единый `Animal*`: реальный (динамический) тип объекта определяется в
runtime, и vtable указывает на правильную переопределённую версию.

### Ключевое слово `override`

`override` (C++11) не обязателен синтаксически, но крайне полезен: он
явно указывает компилятору, что метод должен переопределять виртуальный
метод базового класса, и **вызывает ошибку компиляции**, если сигнатура не
совпадает (опечатка в имени, другой набор параметров, отсутствие `const`).
Без `override` такая ошибка была бы "тихой" — компилятор просто создал бы
новый, независимый метод, скрывающий (а не переопределяющий) метод базового
класса, что привело бы к неверному поведению без предупреждений.

### Виртуальный деструктор — почему он критически важен

Если базовый класс не объявляет деструктор `virtual`, а объект удаляется
через указатель на базовый класс (`delete animalPtr;`, где `animalPtr` типа
`Animal*`, но реально указывает на `Dog`), вызовется **только деструктор
`Animal`**, а деструктор `Dog` (и, соответственно, деструкторы его
собственных ресурсов) не будет вызван — это неопределённое поведение и
потенциальная утечка ресурсов. Объявление `virtual ~Animal() {}` заставляет
компилятор искать реальный (динамический) тип объекта через vtable так же,
как для любой другой виртуальной функции, и вызывать корректную цепочку
деструкторов "снизу вверх" (сначала `~Dog()`, потом `~Animal()`).
**Правило:** если класс предполагается использовать полиморфно (через
указатель/ссылку на базу) — его деструктор обязан быть виртуальным.

### Проблема "срезки" (object slicing)

Если функция принимает объект **по значению**, а не по ссылке/указателю
(`void f(Animal a)` вместо `void f(const Animal& a)`), то при передаче
объекта `Dog` копируется только часть объекта, соответствующая `Animal` —
"хвост", специфичный для `Dog` (`breed` и переопределённые методы),
отбрасывается ("срезается"). Полученная внутри функции копия — это уже
чистый `Animal`, и полиморфное поведение теряется: вызов `a.speak()`
внутри такой функции всегда вызовет `Animal::speak()`, независимо от того,
что было передано изначально. Именно поэтому `makeSound(const Animal&
animal)` в `zadanie2_animal.cpp` принимает параметр **по ссылке** — ссылка
не копирует объект, а лишь "смотрит" на оригинал, сохраняя его настоящий
динамический тип и, соответственно, корректную виртуальную диспетчеризацию.

## 3. Абстрактные классы и чистые виртуальные функции (Задание 3)

**Чистая виртуальная функция** объявляется с `= 0` в конце:

```cpp
virtual double getArea() const = 0;
```

Это означает: "у базового класса нет и не может быть осмысленной реализации
этого метода — каждый конкретный производный класс обязан предоставить
свою". Класс, содержащий хотя бы одну чистую виртуальную функцию,
называется **абстрактным** — создать его объект напрямую невозможно
(`Figure f;` — ошибка компиляции), потому что у объекта такого класса
отсутствовал бы полный, работоспособный набор методов.

Абстрактный класс, состоящий только из чистых виртуальных функций (без
полей и реализованных методов), фактически играет роль **интерфейса** —
контракта, который обязаны выполнить все наследники (пример —
`Printable`/`Serializable` из Задания 4). Если производный класс не
реализует хотя бы одну чистую виртуальную функцию, он сам автоматически
становится абстрактным, и создать его объект тоже будет невозможно —
компилятор принуждает к полной реализации контракта.

Полезность абстракции наглядно видна в `main()` Задания 3: код работает с
`vector<Figure*>`, не зная и не заботясь о том, `Square` это, `Circle` или
`Triangle` — вызов `f->display();` благодаря полиморфизму сам "находит"
нужную реализацию. Это и есть практическая выгода полиморфизма: код,
обрабатывающий фигуры, не нужно менять при добавлении нового вида фигуры —
достаточно создать новый класс, унаследованный от `Figure`.

## 4. Множественное наследование (Задание 4)

C++, в отличие от большинства современных языков (Java, C#), позволяет
классу наследоваться сразу от нескольких базовых классов:

```cpp
class Document : public Printable, public Serializable { ... };
```

Это удобно для реализации **множества независимых интерфейсов** — `Document`
одновременно "умеет печататься" и "умеет сериализоваться", и это две
ортогональные способности, которые естественно выразить как два отдельных
интерфейса.

### Проблема ромбовидного наследования (Diamond Problem)

Если класс `D` наследуется от `B` и `C`, а оба `B` и `C`, в свою очередь,
наследуются от общего класса `A`, то без специальных мер объект `D`
содержит **две независимые копии** данных `A` — одну через `B`, другую через
`C`. Обращение к полю `A` из `D` становится неоднозначным (компилятор не
может понять, через какую копию идти) — отсюда и название "ромб" (`A` на
вершине, `B`/`C` по бокам, `D` внизу).

Решение в C++ — **виртуальное наследование** (`class B : public virtual A`).
Оно гарантирует, что при таком ромбе в объекте `D` будет создана **только
одна** общая копия `A`, разделяемая между `B` и `C`. Однако у виртуального
наследования есть своя цена — усложнение модели памяти объекта и небольшие
накладные расходы на доступ к базовому классу через виртуальную таблицу
смещений, поэтому его применяют только тогда, когда общая база
действительно нужна в единственном экземпляре.

## 5. Практический пример полиморфной бизнес-логики (Задание 5)

`Employee` — хороший пример того, как виртуальные функции заменяют
громоздкие конструкции `if/switch` по типу объекта. Без полиморфизма
пришлось бы писать что-то вроде:

```cpp
if (employee.type == MANAGER) salary = ...;
else if (employee.type == DEVELOPER) salary = ...;
```

и добавлять новую ветку при каждом новом типе сотрудника — нарушение
**принципа открытости/закрытости** (Open/Closed Principle): код должен быть
открыт для расширения, но закрыт для изменения. С виртуальным методом
`calculateSalary()` добавление нового типа сотрудника (например, `Contractor`)
не требует ни единой правки в существующем коде — достаточно унаследовать
новый класс от `Employee` и переопределить нужные методы (это
продемонстрировано в Задании 6, где `Vehicle` расширяется тремя разными
подтипами транспорта без изменения общей логики обхода `vector<Vehicle*>`).

## 6. Принцип подстановки Барбары Лисков (Liskov Substitution Principle)

Один из принципов SOLID гласит: если `S` — подтип `T`, то объекты типа `T`
в программе должны быть заменяемы объектами типа `S` **без нарушения
корректности программы**. Иными словами, наследник обязан вести себя так,
чтобы код, написанный для работы с базовым классом, продолжал работать
корректно и для производного. Все примеры этой практической работы (обход
`vector<Employee*>`, `vector<Figure*>`, `vector<Vehicle*>` без знания
конкретного подтипа) — это прямая демонстрация LSP на практике: клиентский
код полностью не зависит от того, какой конкретно подкласс подставлен.

## 7. Реальные области применения

- **GUI-фреймворки**: базовый класс `Widget`/`View`, от которого
  наследуются `Button`, `TextBox`, `Slider` — общий код отрисовки и
  обработки событий пишется один раз для базового указателя.
- **Игровые движки**: базовый класс `GameObject`, от которого наследуются
  `Player`, `Enemy`, `Projectile` — обновление сцены (`update()`, `draw()`)
  вызывается полиморфно для всех объектов без разбора типов.
- **Плагинные архитектуры и драйверы**: абстрактные интерфейсы (чистые
  виртуальные классы) определяют контракт, а конкретные реализации
  подключаются во время выполнения — ровно так же, как `Printable`/
  `Serializable` в Задании 4.
- **Иерархии исключений** в стандартной библиотеке C++ (`std::exception` →
  `std::runtime_error`, `std::logic_error` и т.д.) — обработчик `catch (const
  std::exception& e)` полиморфно ловит любой производный тип исключения.

## 8. Ответы на вопросы для защиты практической работы

**Что такое наследование? Какие типы наследования существуют в C++?**
Наследование — механизм создания нового класса на основе существующего с
переиспользованием его полей и методов. Типы: `public`, `protected` и
`private` наследование, отличающиеся тем, как понижаются уровни доступа
унаследованных членов в производном классе.

**В чём разница между public, protected и private наследованием?**
При `public` наследовании уровни доступа сохраняются как есть (`public`
остаётся `public`). При `protected` — все унаследованные `public`-члены
становятся `protected`. При `private` — все унаследованные `public`- и
`protected`-члены становятся `private` в производном классе. На практике
почти всегда используется `public`-наследование, моделирующее "является".

**Что такое виртуальная функция? Как она работает?**
Виртуальная функция — метод, который может быть переопределён в
производном классе и вызывается через механизм динамической
диспетчеризации (таблицу виртуальных функций, vtable). Вызов такой функции
через указатель/ссылку на базовый класс определяется реальным
(динамическим) типом объекта в момент выполнения, а не статическим типом
указателя.

**Зачем нужен виртуальный деструктор?**
Чтобы при удалении объекта производного класса через указатель на базовый
класс (`delete basePtr;`) корректно вызывалась вся цепочка деструкторов
(от производного к базовому), а не только деструктор базового класса —
иначе ресурсы производного класса не освободятся (утечка) либо возникнет
неопределённое поведение.

**Что такое абстрактный класс? Как его создать?**
Класс, содержащий хотя бы одну чистую виртуальную функцию (`= 0`). Создать
объект такого класса напрямую нельзя — он может использоваться только как
база для наследников, реализующих все чистые виртуальные функции.

**Что такое чистая виртуальная функция?**
Виртуальная функция без реализации в базовом классе, объявленная с `= 0`,
которая обязывает каждый неабстрактный производный класс предоставить
собственную реализацию.

**В чём разница между статическим и динамическим полиморфизмом?**
Статический полиморфизм разрешается на этапе компиляции (перегрузка
функций/операторов, шаблоны) — компилятор точно знает, какая версия кода
будет вызвана. Динамический полиморфизм разрешается во время выполнения
через виртуальные функции и vtable — конкретная реализация выбирается по
реальному типу объекта в runtime.

**Что такое "срезка" (slicing) и как её избежать?**
Потеря специфичной для производного класса части объекта при копировании
его "по значению" в переменную/параметр базового типа. Избежать можно,
передавая и храня объекты полиморфных иерархий только через указатели или
ссылки на базовый класс, а не по значению.

**Какие проблемы возникают при множественном наследовании?**
Главная — ромбовидное наследование (Diamond Problem), при котором
дублируется общая база, что порождает неоднозначность доступа к её членам.
Решается виртуальным наследованием (`virtual` при указании базового
класса).

**Что такое ключевые слова override и final?**
`override` явно указывает, что метод переопределяет виртуальный метод
базового класса, и заставляет компилятор проверить соответствие сигнатур
(защита от опечаток). `final` запрещает дальнейшее переопределение метода
в производных классах (или наследование от класса, если применён к самому
классу).
