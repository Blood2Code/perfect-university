# Самостоятельная работа: Система анализа больших данных с использованием STL и многопоточности

## 1. Постановка задачи

Тема самостоятельной работы сформулирована открыто: «Разработка системы
анализа больших данных с использованием STL и многопоточности». Такая
формулировка требует не решения конкретного заранее заданного примера, а
**самостоятельного проектирования** содержательной, реалистичной задачи,
где STL-контейнеры/алгоритмы и многопоточность применяются осмысленно, а
не искусственно.

В качестве предметной области выбран **анализ транзакций интернет-магазина**
— реалистичный и понятный пример "больших данных": имеется большой массив
записей о покупках (категория товара, сумма чека), и требуется быстро
получить агрегированную статистику (выручка по категориям, средний чек,
максимальный чек, топ категорий по выручке). Такая задача:

1. Достаточно велика по объёму данных (в решении — 5 000 000 записей), чтобы
   параллельная обработка давала измеримый выигрыш.
2. Естественно распараллеливается — каждая транзакция обрабатывается
   независимо от других.
3. Требует нетривиальной агрегации — что даёт возможность продемонстрировать
   осмысленное сочетание STL-контейнеров (`unordered_map`, `vector`) и
   алгоритмов (`sort`, `accumulate`) с многопоточностью.

## 2. Архитектура решения

### 2.1 Модель данных

```cpp
struct Transaction { string category; double amount; };
struct CategoryStats { double totalRevenue; long long count; double maxAmount; };
using StatsMap = unordered_map<string, CategoryStats>;
```

`Transaction` — минимальная запись о покупке. `CategoryStats` — накопленная
статистика по одной категории, с методами `add()` (учесть новую
транзакцию) и `merge()` (объединить статистику из другого источника —
это и есть ключ к безопасному распараллеливанию, разобранному ниже).
`unordered_map<string, CategoryStats>` выбран вместо `map`, потому что
порядок категорий в промежуточных структурах не важен (сортировка для
вывода делается отдельно, через `sort` уже в конце), а хэш-таблица даёт
`O(1)` в среднем на добавление статистики по категории вместо `O(log n)`
у упорядоченного `map` (подробное сравнение контейнеров — практическая
работа №10, папка 10).

### 2.2 Последовательная версия — базовая точка отсчёта

```cpp
StatsMap analyzeSequential(const vector<Transaction>& data) {
    StatsMap stats;
    for (const auto& t : data) stats[t.category].add(t.amount);
    return stats;
}
```

Простой линейный проход, сложность `O(n)` относительно числа транзакций
(с учётом того, что операции над `unordered_map` — амортизированные
`O(1)`). Эта версия служит эталоном как для проверки корректности
параллельной версии (результаты должны полностью совпадать), так и для
измерения выигрыша от распараллеливания.

### 2.3 Параллельная версия — почему выбрана схема "MapReduce", а не общий
мьютекс

Наивный подход к распараллеливанию выглядел бы так: разбить данные на
части, запустить по потоку на часть, и каждый поток обновляет **одну общую**
`StatsMap`, защищённую единственным `mutex`. Этот подход **правильный, но
крайне неэффективный**: при большом количестве транзакций каждый поток
захватывал бы общий мьютекс миллионы раз, и потоки фактически
сериализовались бы на этом мьютексе — параллелизм был бы утрачен почти
полностью (это прямое применение вывода из практической работы про
многопоточность, папка 12: минимизация числа синхронизаций критична для
реального ускорения).

Вместо этого решение использует классическую схему **Map → Reduce**,
лежащую в основе промышленных систем обработки больших данных (Hadoop,
Apache Spark, и в упрощённом виде — `ParallelSumCalculator` из
практической работы №12):

1. **Map-этап (параллельно, без синхронизации):** каждый поток обрабатывает
   свой непересекающийся диапазон транзакций и строит **собственную,
   локальную** `StatsMap` (`vector<StatsMap> localStats(numThreads)`).
   Потоки не обращаются к чужим локальным картам — гонки данных
   структурно невозможны, поэтому **мьютекс на этом этапе вообще не
   нужен**.
2. **Reduce-этап (последовательно, один раз):** после того как все потоки
   завершились (`for (auto& t : threads) t.join();`), главный поток
   один-единственный раз проходит по всем `numThreads` локальным картам и
   объединяет их в общий результат методом `merge()`. Поскольку число
   уникальных категорий мало (в примере — 6), этот этап занимает
   пренебрежимо малое время по сравнению с обработкой миллионов
   транзакций.

Именно поэтому в замерах параллельная версия ускоряется почти
пропорционально числу потоков (в тестовом запуске — примерно в 5,6 раза
на 10 логических ядрах), а не деградирует из-за конкуренции за мьютекс,
как это было бы при наивном подходе "общая карта + один мьютекс на каждую
транзакцию".

### 2.4 Разбиение данных на потоки

```cpp
size_t chunkSize = n / numThreads;
for (unsigned i = 0; i < numThreads; ++i) {
    size_t start = i * chunkSize;
    size_t end = (i == numThreads - 1) ? n : start + chunkSize;
    ...
}
```

Данные делятся на примерно равные непрерывные блоки. Последний поток
получает "остаток" от целочисленного деления (`n % numThreads`), чтобы не
потерять "хвостовые" элементы — тот же приём, что и в `ParallelSumCalculator`
из практической работы №12. Число потоков берётся через
`thread::hardware_concurrency()` — стандартный способ узнать количество
логических ядер процессора во время выполнения, что делает программу
переносимой между машинами с разным числом ядер, а не жёстко "зашитой"
под конкретное количество потоков.

## 3. Использование STL сверх многопоточности

Помимо `unordered_map`, решение сознательно опирается на изученные ранее
элементы STL (см. практические работы №10–11):

- **`vector<Transaction>`** — основное хранилище "больших данных",
  выбранное за непрерывность в памяти (кэш-дружественность при линейном
  переборе, критично для производительности при миллионах записей) и
  `O(1)` доступ по индексу (нужен для разбиения на диапазоны `[start, end)`
  по потокам).
- **`sort` с лямбда-компаратором** — для получения топа категорий по
  выручке в `printReport()`.
- **`accumulate` из `<numeric>`** — для подсчёта общей выручки по всем
  категориям одной строкой вместо ручного цикла.
- **`std::mt19937` + `uniform_real_distribution`** — генератор
  синтетических "больших данных" с фиксированным зерном (`42`) для
  воспроизводимости результатов между запусками (без этого сравнение
  времени выполнения между последовательной и параллельной версией было
  бы не совсем корректным, если бы каждый раз генерировались разные
  случайные данные).

## 4. Проверка корректности

Ключевой критерий правильности параллельной реализации — **её результат
должен побайтово совпадать с результатом последовательной версии**. В
проведённом тестовом запуске оба отчёта (`printReport` для `seqStats` и
`parStats`) выводят идентичные значения выручки, количества чеков и
максимального чека по каждой категории — это подтверждает, что схема
Map-Reduce реализована корректно и не теряет и не дублирует ни одной
транзакции.

## 5. Анализ сложности и производительности

- Последовательная версия: `O(n)` по времени (один проход по `n`
  транзакциям, амортизированные `O(1)` операции над `unordered_map`),
  `O(k)` по дополнительной памяти (`k` — число уникальных категорий).
- Параллельная версия: `O(n / p + k · p)` по времени, где `p` — число
  потоков: `O(n/p)` — время работы каждого потока на своей доле данных
  (в идеале выполняется одновременно на разных ядрах), `O(k · p)` — время
  reduce-этапа (перебор `p` локальных карт, в каждой не более `k`
  категорий). Поскольку `k` (число категорий) на порядки меньше `n`
  (число транзакций), reduce-этап пренебрежимо дёшев, и итоговое время
  практически линейно уменьшается с ростом `p` — что и наблюдается в
  измерениях.
- **Закон Амдала** объясняет, почему ускорение не строго равно числу
  потоков: небольшая "последовательная" часть программы (генерация
  данных, reduce-этап, вывод отчёта) не распараллеливается и ограничивает
  максимально достижимое ускорение снизу.

## 6. Почему это релевантно реальным системам обработки больших данных

Схема "разбить данные на части → обработать независимо → объединить
результат" — это не учебное упрощение, а **фундаментальный паттерн**,
лежащий в основе промышленных систем обработки больших данных:

- **Apache Hadoop MapReduce** и **Apache Spark** реализуют ровно эту же
  идею, но на уровне кластера из множества машин, а не потоков одного
  процесса: данные делятся на партиции, каждая обрабатывается независимым
  worker'ом (аналог потока в нашем решении), а результаты агрегируются
  на этапе reduce.
- **Параллельные СУБД и аналитические движки** (ClickHouse, аналитические
  запросы в PostgreSQL) применяют тот же принцип для параллельного
  выполнения агрегатных запросов (`GROUP BY`, `SUM`, `COUNT`) по большим
  таблицам, разбивая таблицу на сегменты между потоками/ядрами.
- **Библиотеки для локального параллелизма** (Intel TBB, OpenMP) реализуют
  примитивы, автоматизирующие ровно такую же схему "локальная агрегация +
  финальное слияние" без необходимости писать её вручную, как это сделано
  в учебных целях в данном решении.

Таким образом, задание, сформулированное открыто ("анализ больших данных
с использованием STL и многопоточности"), решено через демонстрацию
паттерна, который масштабируется от учебного примера на одной машине с
несколькими потоками до промышленных распределённых систем обработки
данных — при полностью одинаковой логической схеме "map локально, reduce
глобально один раз".
